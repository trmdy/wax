## The operation

One op: `export` gains an optional `overrides` array — a set of edited
cell values layered over the read model before the writer runs.

- Capability is advertised additively as `caps:["exportOverrides"]` on the
  `version` and `open` responses. Absence of `caps` means no capabilities.
  **No proto bump** — the field is additive and backward compatible.
- `overrides: [{sheet, r, c, v}]` — zero-based absolute indices.
- `v` is a JSON `number | string | boolean | null`; `null` clears the cell.
- Strings beginning with `=` are stored as **text**, never reinterpreted as
  formulas (apiary phase-2 policy). wax gets this for free:
  `rust_xlsxwriter` only treats a value as a formula through its `Formula`
  type, and `write_string` never reinterprets.
- Overriding a formula cell **drops the formula** in favour of the literal
  value, recorded in `dropped[]` (e.g. `"formulas replaced by edited
  values (3)"`).
- Overrides may extend the used extent, subject to the existing
  extent/bomb caps — structured refusal, never silent clipping.
- The response carries an `applied` count.
- `overrides.length` is capped (≥100k suggested); breaching it is
  `bad_request` naming the cap.
- `format:"csv"` accepts the same field.

## The six amendments (all binding)

**A1 — display-string recompute (the highest-risk item).** Our model
carries a per-cell display string `d`, rendered by wax-fmt from the source
value + format code at *read* time, and `write_csv` is display-else-raw.
An override that replaces `v` without touching `d` would make CSV export
the **old** value while xlsx exports the new one. Therefore: an override
replaces `v` **and recomputes `d`** by re-rendering the retained format
code through wax-fmt. With no retained format code, `d` becomes null and
CSV falls back to raw.

**A2 — style and format retention.** Overriding an existing cell keeps its
style id (`WindowCell.s`) and format code (`fmt`) — apiary edits a value,
not the formatting. A cell created beyond the original extent has neither
and lands on the XF-0 base style (the W4D convention). No inheritance of
column/row styling is implied.

**A3 — numeric `v` is never coerced to a date.** A number is stored as a
number (`t:"n"`) even into a date-formatted cell; the retained format code
makes Excel — and wax's own reader on read-back — display and type it as a
date, which is Excel's own semantics. This keeps overrides free of
1900/1904 epoch ambiguity and needs no new wire type. Strings are likewise
never date-sniffed (consistent with the `=` rule). A consumer wanting a
real date write sends the serial and relies on the cell's format.

**A4 — determinism for duplicates.** Two overrides for the same
`(sheet, r, c)` are last-wins in array order; `applied` counts
post-collapse distinct cells written, not raw array length.

**A5 — split error taxonomy.** `overrides.length` over cap, unknown sheet
index, or a malformed entry ⇒ `bad_request` naming the cap/index/field.
Extent growth breaching the cell caps ⇒ `too_large` or `bomb`, whichever
existing rail fires (those codes already carry that meaning; `bad_request`
there would overload an existing failure). An out-of-range sheet is
`bad_request`, never a silent skip.

**A6 — CSV scope.** `wax export --format csv` writes one sheet. Overrides
targeting other sheets are ignored, not rejected (apiary holds one edit set
for the whole workbook), and `applied` counts only the exported sheet.

## Two notes (also committed)

1. The W5D oversized-string policy applies to overrides: a string over
   32,767 characters truncates on a character boundary with a loud
   `dropped` entry, and the export still succeeds.
2. **Do not** add `caps` to the `wax --version` line. The release workflow
   validates it against `^wax <semver> \(proto <n>\)$`; a third field
   breaks the tag build. `caps` belongs in JSON responses only.

## Implementation note (carried into the contract)

Apply overrides as a **layer inside the writer's existing scan**:
`write_xlsx` already iterates via `WorkbookStore::scan_sheet`, so merge the
override map over each visited cell, then emit the remaining out-of-extent
overrides as synthesized cells and recompute sheet dims as
`max(store dims, override max + 1)`.

**Do not mutate the store.** Export must stay side-effect-free so a second
export of the same handle is unaffected — the store is shared across
handles and windows, and the W4 writer's atomic temp+persist output
semantics assume a stable input model.
