# wax v0.5 — authored formulas (+ recalc display strings)

- **Status:** operator contract, frozen 2026-08-04 (CL.161). Consumer: apiary
  Sheet P5 (`docs/sheet/SPEC-P5.md`), which is building the authoring UI now
  and is capability-gated on this.
- **Precedent discipline:** v0.2/v0.3/v0.4 contracts — caps in JSON responses
  only (never the `--version` line), additive fields, loud structured
  refusals, zero corpus regression, release via the workflow with verified
  artifacts.

## Why

v0.4 evaluates formulas that came FROM the file and recalculates dependents
when a literal override changes. It cannot express an AUTHORED formula.
Verified against the shipped 0.4.0 binary:

- `recalc` override entry with `f` → `bad_request: overrides[0].v must be a
  number, string, boolean, or null`.
- `recalc` override with `v: "=1+2"` → accepted, stored as TEXT per the
  frozen v0.2 rule; the dependent recomputed as if the cell were text.

A human typing `=SUM(A1:A3)` into apiary therefore cannot be served today.

## Scope 1 — authored formulas (`caps: ["authoredFormulas"]`)

Override entries gain an optional `f`:

```jsonc
{"sheet":0,"r":4,"c":2,"f":"=SUM(A1:A3)"}          // authored formula
{"sheet":0,"r":4,"c":2,"f":"=SUM(A1:A3)","v":6}    // formula + caller's last known value
{"sheet":0,"r":4,"c":2,"v":42}                      // literal, unchanged v0.2 semantics
```

- `f` present → the entry is a FORMULA. Its source is parsed and evaluated by
  the v0.4 engine; the cell joins the dependency graph so dependents of it
  recompute, and it recomputes when ITS precedents change.
- `f` absent → exactly today's literal semantics, including the frozen rule
  that a `v` string beginning with `=` stays TEXT. That rule is unchanged and
  remains the default; `f` is the only way to author.
- `v` alongside `f` is advisory only (caller's cached value); the engine's
  computed result always wins.
- Applies to BOTH `recalc` and `export`. On export, an authored formula is
  written as a real formula with its computed value cached — NOT flattened to
  a literal. This supersedes, for `f` entries only, the v0.2 rule that
  overridden formula cells drop their formula (that rule still governs
  literal overrides landing on formula cells).
- Unparseable `f`, or a function outside the curated set → the cell evaluates
  to the engine's error value (`#NAME?` etc.) and is reported in the response;
  it is NOT a request-level failure. Malformed entry shape stays
  `bad_request`, per the A5 taxonomy.
- Cycles introduced by authored formulas produce `#CYCLE!` exactly as
  file-authored cycles do — never a hang.

## Scope 2 — display strings on recalc (bug/gap)

`recalc` currently returns `d: null` on every changed cell (verified on
0.4.0), which forces the consumer to render raw values and lose number
formats. Per the v0.2 A1 rule — an override REPLACES `v` and RECOMPUTES `d`
through wax-fmt with the retained format code — `recalc` must populate `d`
the same way: re-render through the cell's retained format, `null` only when
no format code is retained. Authored-formula cells with no retained format
render General.

## Gate

1. Authoring works end to end: an authored formula evaluates, participates in
   the dependency graph both directions, and survives export as a real
   formula with a cached value that re-opens correctly.
2. `d` populated on recalc per the A1 rule; a regression test proves a
   format-carrying cell keeps its formatting through recalc.
3. Error paths honest: unknown function, syntax error, and authored cycle each
   produce engine error values reported in the response, not request failures
   or hangs. Fuzz the authored-formula path (extend the existing formula
   parser fuzz target with override-sourced input).
4. Zero corpus regression on every existing counter; new scoreboard row for
   authored-formula round-trip if cheap.
5. v0.5.0 released via the workflow, artifacts verified from published URLs,
   `--version` exactly `wax 0.5.0 (proto 0)`, caps gain `authoredFormulas`.
6. Seal with the checklist, release URL, and a forwardable apiary one-liner.

## Operator close-out (2026-08-04, CL.161) — shipped behavior

Reviewed against the release binary before tagging. Two divergences from the
text above were found and are recorded here rather than silently shipped.

### 1. `changed[]` includes literal overrides (contract amended to match)

The binary echoes literal (`f`-absent) overrides back in `changed[]` with
`e: false`, alongside engine-computed entries. The operator ruled twice for
dependents-only and the implementor shipped additive; with the implementor
sealed and gone, the contract is amended to match the binary rather than
leaving text and code disagreeing.

Consumers must therefore treat `changed[]` as "the post-recalc state of every
cell this request touched or recomputed", not "cells the engine computed".
Apiary's consumer already tolerates both shapes (it requires the dependent
and ignores extras), so this needs no client change.

**Known cost, filed for a follow-up:** the 50k cap is shared, so a large
literal paste spends the budget echoing values the caller already has — a
40k-cell paste returns ~40k echoes plus dependents and can truncate real
results. If that becomes a practical limit, revisit dependents-only.

### 2. `d` is null on recalc — NOT a regression

Investigated directly: the fixture's formula cells carry no display string on
the READ path either, so recalc returning `d: null` for them is consistent
rather than a scope-2 failure. Literal number cells DO carry `d` on read
while formula cells do not — a pre-existing asymmetry in the read path, not
something v0.5 introduced. Low impact while these cells are General-format;
worth revisiting if formatted formula cells are ever rendered from `d`.
